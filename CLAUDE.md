## Architecture

Desktop Tkinter app that turns photographed/scanned "master card release" sheets into a structured XLSX. Pipeline, implemented as a strict one-way chain of independent modules, orchestrated only by `ui/app.py`:

```
ocr/image_processor (OpenCV preprocessing)
  → ocr/engine (PaddleOCR 3.x → OCRResult: texto + confiança + box)
  → parsing/registro_parser (groups OCRResults into table rows by spatial position)
  → validacao/regras (classifies each Registro: CONFIRMADO / REVISAO; validates data via tempo_parser)
  → exportacao/xlsx_exporter (writes the 3-sheet workbook, preserving the sheet's physical order)
```

`ocr/pdf_reader.py` and `dados/data_manager.py` feed into this chain independently (PDF→image generator; XLSX reference lookups), and `main.py` just launches `leitor_matriculas.ui.app.App`.

**Fase 5 — reorganização arquitetural (layout only, zero behavior change)**: the flat root-level modules were moved into `src/leitor_matriculas/`, grouped by responsibility — `ocr/` (image_processor, engine, pdf_reader), `parsing/` (registro_parser, tempo_parser), `validacao/` (regras, correspondencia_aproximada), `dados/` (data_manager), `exportacao/` (xlsx_exporter, csv_exporter), `ui/` (app). Module paths below are relative to that package. Renames: `ui.py`→`ui/app.py`, `ocr_engine.py`→`ocr/engine.py`, `validacao.py`→`validacao/regras.py`, `exporter.py`→`exportacao/csv_exporter.py` (avoids `validacao.validacao`-style stutter). The dependency graph is one-way and verified acyclic: `parsing→ocr`, `validacao→parsing`, `ui→everything`. Two migration details that are easy to break:
  - the project runs straight from the directory with **no pip install**, so `main.py` prepends `src/` to `sys.path` and every test script does `sys.path.insert(0, .../"..", "src")`;
  - `DataManager` resolves the real `dados/` folder from `__file__` and it now sits **three levels up** (`dados/`→`leitor_matriculas/`→`src/`→root). Moving `dados/data_manager.py` to a different depth breaks the lookup silently — the app would just report empty bases.
  Tests keep their original location (`teste/`), unchanged behavior; only their imports, `sys.path` and `patch()` target strings (`'ui.X'`→`'leitor_matriculas.ui.app.X'`) were updated.

**Design invariant across every module**: never invent or guess data. Anything that can't be confirmed with certainty is routed to manual review (`REVISAO`) rather than auto-corrected — this shows up repeatedly (conservative bbox-distance cutoffs in `parsing/registro_parser.py`, `normalizar_matricula` refusing to touch non-matricula-looking text, `tempo_parser` refusing to guess a missing year, and the fuzzy matching in `validacao/correspondencia_aproximada.py` refusing to pick between two similarly-close candidates).

**Fase 1 — precisão da extração das 8 liberações** (see module contracts below for specifics): the sheet is a printed form with a fixed structure of 8 liberação rows × 5 handwritten fields. This phase added, incrementally, on top of the still-generic full-page-OCR + spatial-parser pipeline (Estratégia A from the analysis that preceded it — full template/ROI extraction was deliberately deferred, not adopted):
  - printed text (titles, form code, footer) rejected from ever becoming a fake DATA/HORA value or a phantom registro (`parsing/registro_parser.py`: format gate + `linhas_ignoradas`);
  - 8-per-page is used only as a validation signal (`verificar_contagem_posicoes`), never to fabricate or drop a registro;
  - MOTIVO and RESPONSÁVEL get a controlled fuzzy match against their base lists when the exact match fails (`validacao/correspondencia_aproximada.py`, wired into `validacao/regras.py`) instead of unconditionally going to REVISAO on any OCR noise;
  - a DATA+HORA pair glued into a single OCR box (a real detector-level artifact, not a parser bug) is split only when both halves independently validate (`tempo_parser.tentar_separar_data_hora_mesclada`, applied in `ui/app.py`).
  Known residual limitation from this phase: free-text columns (MOTIVO/RESPONSÁVEL) have no format gate the way DATA/HORA do, so a printed fragment can still occasionally land in one of those columns if it's the only candidate in an otherwise-empty footer row; it has never been observed to cause a false CONFIRMADO (the resulting registro still lacks a matrícula), but it is not fully eliminated. See the Fase 1 report for the real-photo evidence.

**Fase 2 — reconciliação de requisitos (spec ⇄ código)**: two "definitive functional requirements" were contradicting each other across README/CLAUDE.md/code. Both were resolved in favor of the README (the code was the side that had drifted):
  - **HORA is OPTIONAL, DATA is mandatory.** Absent *or illegible* hora never blocks `CONFIRMADO` — if data/matrícula/motivo/responsável are confirmed, the record is confirmed without any hora. Previously `tempo_parser.validar_data_hora` treated an empty hora as a blocking error, sending every hora-less liberação to REVISAO against spec. That function was **replaced** by the pair `validar_data` (blocking) + `avaliar_hora_opcional` (never blocking). An illegible hora is exported as an **empty cell**, never as the raw OCR text (which would be indistinguishable from a real hora) — but the raw text is preserved in the Observação, so nothing is silently lost. `ResultadoValidacao.hora_confirmada` carries the usable value (or `None`), following the same pattern as `.motivo_confirmado`/`.gestor_confirmado`, and is evaluated **before** every early return so a legitimate hora survives a REVISAO caused by some other field.
  - **The sheet's PHYSICAL order is preserved; there is no chronological sorting.** `xlsx_exporter` no longer reorders anything (`_ordenar_cronologicamente`/`_chave_ordenacao_cronologica` were removed) — rows are written exactly as received, which is the parser's top-to-bottom reading order per page and the page order across the batch. This is what lets the spreadsheet be checked against the paper line by line. Do not reintroduce sorting by date, name, matrícula, gestor, or motivo.
  Side effect: `tempo_parser.interpretar_data_hora` no longer has any production caller (it was the sort key). It's kept as a tested utility and flagged in its own docstring as a dead-code removal candidate.

**Definitive functional requirement — read-from-sheet vs. derived-from-lookup**: only DATA, HORA, MATRÍCULA, MOTIVO and RESPONSÁVEL (gestor) are handwritten data the OCR is meant to recognize. NOME and SETOR are never read from the sheet — they are always derived by looking up the recognized MATRÍCULA in `Colaboradores.xlsx` (a PROCV/XLOOKUP-style join, in `data_manager.buscar_colaborador`). This is enforced structurally in `parsing/registro_parser.py`: `CAMPOS_TODOS` (the fields exposed to callers) excludes `nome`/`setor`, even though the header-detection step still locates those columns' x-position internally (`CABECALHOS_CONHECIDOS` keeps them, `CAMPOS_IGNORADOS_NA_SAIDA` strips them back out after association) — this is not optional plumbing, it's what stops a NOME/SETOR-column text from bleeding into the neighboring MATRÍCULA/MOTIVO column once those two fields stop being "real" destinations. When a matrícula isn't found in the base, `ui/app.py` shows an explicit `"(não encontrado)"` placeholder for nome/cargo/setor rather than a blank string — an unconfirmed value must never look like "genuinely empty but valid".

**Module contracts** (each is independently testable and deliberately decoupled from its neighbors):
- `ocr/image_processor.py` — OpenCV preprocessing (grayscale, denoise, CLAHE, sharpen); never mutates the input image, returns a new one. Adaptive threshold is off by default (destroys thin pen strokes on handwriting).
- `ocr/engine.py` — `OCREngine` ABC wraps PaddleOCR 3.x behind `recognize(image) -> List[OCRResult]`, so the engine could be swapped later. **Written specifically for PaddleOCR's 3.x `predict()` API** (`requirements.txt` pins `paddleocr>=3.7.0,<4.0.0` on purpose) — the 2.x `ocr.ocr()` API has a different constructor and return shape; do not downgrade. Also holds `parece_matricula()`/`normalizar_matricula()`, a conservative heuristic for fixing common handwritten OCR confusions (O↔0, I/l↔1, S↔5, B↔8) — applied only to text that already looks like a matricula, never to names/columns.
- `parsing/registro_parser.py` — pure spatial parser: takes the flat `OCRResult` list (unordered) and reconstructs table rows using only bounding-box geometry (vertical-overlap grouping into lines, header-row detection via known column labels in `CABECALHOS_CONHECIDOS` — matched by **substring**, not equality, since the real printed header is a full phrase like "RESPONSÁVEL PELA AUTORIZAÇÃO" that OCR may add noise to, then greedy nearest-column association bounded by `_distancia_maxima_padrao`). Has zero dependency on PaddleOCR — only touches the `OCRResult` dataclass — and does no calendar/database validation itself. A `Registro` is "complete" iff it has a `matricula` field; nothing else is required. Only exposes `matricula`/`gestor`/`motivo`/`data`/`hora` as named fields (see functional requirement above) — `nome`/`setor` text is detected for column geometry only, then always moved to `nao_associados`. **Fase 1 additions**: the DATA/HORA columns have a loose FORMAT gate (`_PARECE_DATA`/`_PARECE_HORA` — structure only, not calendar validity) so printed text without digit-separator-digit structure can never be associated to those columns; a data row that ends up with zero associated fields when a header WAS detected is not turned into a registro at all — it's kept, unmodified, in `ResultadoParser.linhas_ignoradas` (never silently dropped, just kept out of `registros`); `verificar_contagem_posicoes(quantidade_encontrada)` compares against `POSICOES_ESPERADAS_POR_FOLHA = 8` and returns a warning string (or `None`) — purely informational, never used to fabricate or discard a registro.
- `parsing/tempo_parser.py` — structured DATA/HORA interpretation (`interpretar_data`/`interpretar_hora`/`interpretar_data_hora`/`validar_data`/`avaliar_hora_opcional`), independent of everything else. **Fase 2**: `validar_data` is the *blocking* check (DATA is mandatory); `avaliar_hora_opcional` **never blocks** (HORA is optional) — it returns `None` for an absent *or* valid hora, and a warning string (carrying the raw OCR text) only when a hora is present but unreadable. These two replaced the old `validar_data_hora`, which wrongly treated a missing hora as a blocking error. Same "never invent" invariant: a 2-digit year is expanded to 20xx (the digit is genuinely on the page, just abbreviated — not a guess), but a date with **no year at all is rejected**, not defaulted to "this year" — there'd be no way to tell that apart from an actual guess. Impossible dates/times (`date()`/`time()` raising `ValueError`) and unparseable formats both return `None`. **Fase 1 addition**: `tentar_separar_data_hora_mesclada(texto)` handles a real OCR-detector artifact where DATA and HORA get glued into a single box (e.g. `"14.04 26 20:24"`) — it locates loosely-shaped date/hora substrings, reconstructs canonical strings from the digits actually present (never invents a digit), and only returns a split when **both** halves independently pass the same strict `interpretar_data`/`interpretar_hora`; called from `ui/app.py`, not from `parsing/registro_parser.py` (keeps the parser decoupled from date semantics).
- `parsing/contexto_lote.py` (Fase 9) — the only stateful module in the chain, and deliberately tiny: `ContextoLote` accumulates what the sheets ALREADY PROCESSED in this batch prove — today, only the year of their dates. `registrar_data` counts only dates that `interpretar_data` accepts IN FULL (a context-completed date never feeds the context back, or one bad year would propagate through the batch). `ano_do_lote()` elects a year only when it is predominant with margin (`MAXIMO_DATAS_DIVERGENTES = 2` divergent dates tolerated as OCR misreads, AND at least `FATOR_PREDOMINANCIA = 3`× more dates than those, AND at least `MINIMO_DATAS_CONFIAVEIS = 3` — the combination is what separates "one or two years read wrong among dozens of identical ones" from "a batch that genuinely crosses New Year", which must elect no year at all). `completar_ano(texto)` turns a year-less `"23.04"` into canonical `dd/mm/aa` — the completed date still goes through `interpretar_data`, so `"30.02"` + the batch year is still refused. `ano_divergente_do_lote(texto)` is the inverse and equally conservative direction: a date whose year IS written but disagrees with the batch is reported so the caller can send it to REVISAO — the year is never rewritten. Knows nothing about OCR, registros or the spreadsheet; takes and returns text. Owned by `App` (`self._contexto_lote`), fed with a whole page before that page's rows are classified, and reset by "Limpar resultados" — it must never cross two different batches.
- `dados/data_manager.py` — loads the 3 reference workbooks from `dados/` (`Colaboradores.xlsx`, `Gestores.xlsx`, `Motivos.xlsx`) read-only. Column names are matched against configurable candidate-lists (`COLUNAS_CANDIDATAS_*` at the top of the file) rather than hardcoded — **update those lists, not the surrounding logic**, if real spreadsheets use different headers. Never raises to callers: load failures accumulate as strings in `self.avisos` and the corresponding collection stays empty. Matricula is always kept as text (never int/float) to avoid losing leading zeros.
- `validacao/correspondencia_aproximada.py` (Fase 1) — controlled, contextual fuzzy matching used **only** for MOTIVO and RESPONSÁVEL against their closed candidate lists (never for matrícula, nome, setor, or open-ended text). `buscar_correspondencia(texto_ocr, candidatos)` normalizes (uppercase, strip accents), scores every candidate with `difflib.SequenceMatcher` (stdlib, no new dependency), and returns one of `EXATA`/`APROXIMADA`/`AMBIGUA`/`SEM_CORRESPONDENCIA`/`SEM_CANDIDATOS`/`VAZIO`. `AMBIGUA` fires whenever the best and second-best candidates are closer than `MARGEM_AMBIGUIDADE_PADRAO` — it never guesses between two similarly-plausible candidates. Thresholds (`LIMIAR_MINIMO_PADRAO = 0.55`, margin `0.08`) were tuned empirically against real `Motivos.xlsx`/`Gestores.xlsx` content and real printed-form noise (see Fase 1 report) — revisit them together if either base changes shape drastically.
- `validacao/recuperacao_matricula.py` — contextual recovery of the MATRÍCULA when the OCR hands back characters that aren't digits. The final matrícula may contain **only** `0-9`, but the odd characters must NOT be simply deleted — they usually ARE a misread digit, and dropping one changes the number into a different person's ("1954+" stripped to "1954" is a real 4-digit matrícula). Real observed case: the handwritten crossed 7 comes out as `+`. `resolver_matricula(texto, existe_na_base)` generates every plausible digits-only reading from a CLOSED confusion table (`+`→7 or 4; `O`→0, `I`/`l`/`|`→1, `S`→5, `B`→8; `.`/`-`/space are pen noise, removed — never a digit) and asks the caller which exist in the base: exactly one → `RECUPERADA`; two or more → `AMBIGUA` (two possible people — choosing would be the "wrong CONFIRMADO" the system exists to avoid); none → `SEM_CORRESPONDENCIA`, which reaches REVISAO through the normal "matrícula não encontrada" path. `MAXIMO_LEITURAS = 16` caps the combinatorial blow-up — "many possible readings" is itself evidence that there is no safe recovery. Does not import `DataManager`: the existence check arrives as a function, which keeps it testable without any spreadsheet and keeps the dependency direction intact.
- `validacao/regras.py` — classifies a `Registro` as `CONFIRMADO`/`REVISAO` against `DataManager` data. **Fase 2 order**: HORA is evaluated first (via `avaliar_hora_opcional`) precisely because it never blocks — the result is threaded through *every* return below it, so a valid hora is never lost to a REVISAO triggered by another field. Then completeness, then DATA validity (via `tempo_parser.validar_data` — a date that can't be safely interpreted sends the record to REVISAO; an unreadable hora only adds a warning to the Observação), then matrícula lookup/confidence, then gestor and motivo **independently** against the loaded lists (Fase 1: each goes through `correspondencia_aproximada.buscar_correspondencia` — exact match first, controlled fuzzy match second; neither field's failure short-circuits the other, so an accepted motivo correction isn't lost just because gestor still needs review). `CONFIANCA_MINIMA_MATRICULA = 0.80` is the OCR-confidence floor. Missing/unavailable reference data never blocks confirmation by penalizing — it just can't confirm. Returns a `ResultadoValidacao` — a tuple subclass, so `status, observacao = classificar_registro(...)` (the original 2-tuple contract) still works unchanged everywhere — that also exposes `.motivo_confirmado`/`.gestor_confirmado` (the fuzzy-accepted value, or `None` when no correction was needed/possible) and `.hora_confirmada` (Fase 2: the hora text when safely interpretable, `None` when absent or illegible) for whoever builds the export row.
- `validacao/confirmacao.py` (Fase 24a — Web MVP) — `confirmar_revisao_manual`, extracted from `ui/app.py::_revisao_confirmar` so the Tkinter UI and the web backend call the exact same confirmation decision instead of duplicating it. Rebuilds a synthetic `Registro` from the edited fields (confidence 1.0 — human-verified), preserves the record's original `nao_associados` (Fase 12 — without this, manual confirmation would be a backdoor around the campo-perdido block), and reruns `classificar_registro`; only flips a record to `CONFIRMADO` when the result is genuinely that. Also owns `NAO_ENCONTRADO` (the Nome/Cargo/Setor placeholder) as its canonical definition — both `ui/app.py` and `pipeline.py` import it from here so the two interfaces can never show different placeholder text. Calls `dados.registro_correcoes.registrar_correcao` (Fase 20 H5) after the decision is made, same as before the extraction — this is the only place in the whole codebase that does.
- `validacao/explicacao_revisao.py` (Fase 18; relocated from `ui/explicacao_revisao.py` in Fase 24c — Web MVP) — translates the evidence dossier (Fase 17) into operator-facing language: `explicar(evidencias, observacao)` returns the blocking field(s), the OCR-read chain, normalization, and base lookup, in prose; `sinais_de_contexto(registros, indice)` returns the two Fase 16-approved context signals (`gestores_do_lote`, `ordem_cronologica_da_folha`) as `Evidencia` objects — informational only, never pre-selects anything. Never imported Tkinter even when it lived under `ui/`; moved to `validacao/` in Fase 24c specifically so the web backend (`web/backend/rotas/lotes.py`, endpoint `GET /lotes/{id}/registros/{indice}/explicacao`) can call it without depending on `leitor_matriculas.ui` (the one-way dependency graph — nothing may import from inside `ui/`). `ui/app.py` only changed its import line; no logic changed.
- `pipeline.py` (Fase 24a — Web MVP) — "run the pipeline over one sheet": `processar_uma_pagina` (preprocess → OCR → spatial parse → `reparar_data_hora_mescladas`, extracted from `ui/app.py::_processar_uma_pagina`/the module-level `_reparar_data_hora_mescladas`) and `montar_registro_exportacao` (per-`Registro` classification → export dict, extracted from `ui/app.py::_adicionar_registros`'s inner loop), plus the trivial `registro_erro_pagina` helper. Introduces no new business rule — it only orchestrates existing, untouched modules (`ocr.image_processor`, `ocr.engine`, `parsing.registro_parser`, `parsing.tempo_parser`, `validacao.regras`, `validacao.recuperacao_matricula`) in the same order they always ran in. Exists because the web backend needs this exact sequence and cannot import `ui/app.py` (instantiating `App` opens a Tkinter window) — both the desktop worker thread and the FastAPI background thread call these same functions now. Deliberately does NOT own OCR-engine caching or `DataManager`/`ContextoLote` lifetime — those stay the caller's responsibility (`App._ocr_engine`/`self._data_manager` per session; `web/backend/estado.py`'s process-wide singletons + per-`lote_id` `ContextoLote`), since that's resource management, not a business rule.
- `ocr/pdf_reader.py` — `iterar_paginas()` is a generator (via PyMuPDF/`fitz`) that renders one page at a time so a ~200-page monthly PDF is never fully loaded into memory. A single page failing to render yields a `PaginaPdf(erro=...)` and the generator continues; only whole-document failures (bad file, zero pages) raise.
- `exportacao/xlsx_exporter.py` — pure formatter (**not** a sorter): takes a list of already-assembled dicts (built in `ui/app.py` from `Registro` + `classificar_registro` output) and writes them **in the exact order received** — Fase 2 removed the chronological reordering, because the mandated output order is the sheet's physical liberação sequence (parser reads top-to-bottom per page; pages follow the batch order). It writes `Liberações` (all rows) / `Revisão` (REVISAO+ERRO rows) / `Resumo` (counts, breakdowns by gestor/motivo, plus a Fase 1 "páginas com contagem divergente do esperado" count) sheets. The first 7 columns of `COLUNAS` are a fixed, mandated order — Data, Hora, Matrícula, Nome, Setor, Motivo, Responsável — with everything else (Cargo, Página, Status, confidences, Observação, raw OCR text) kept after those as audit/technical info. Does no reading or inference beyond that.
- `exportacao/csv_exporter.py` — a simpler CSV exporter that exists but is **not wired into the UI** currently.
- `ui/app.py` — the only module allowed to import/coordinate the others (still true after Fase 24a: `pipeline.py`/`validacao/confirmacao.py` are neutral, coordinate nothing themselves — `ui/app.py` and the web backend each do their own coordinating around them). OCR runs on a background `threading.Thread`; results cross back to the main thread exclusively via `queue.Queue` + `self.after(...)` polling — the worker thread must never touch Tkinter widgets directly. Multiple image/PDF selections accumulate into the same in-memory result table until "Limpar resultados" is used. The live results table is independent of the export column order (it leads with Página/Status for quick monitoring during processing) — only the exported XLSX is required to follow the mandated 7-column order. **Fase 1 additions**: `_processar_uma_pagina` runs the DATA+HORA merge-split right after parsing (before validação); `_adicionar_registros` uses `resultado_classificacao.motivo_confirmado`/`.gestor_confirmado` when building the table row / export dict, falling back to the raw OCR text when no correction applied; **Fase 2**: the Hora column comes from `resultado_classificacao.hora_confirmada or ""` — never from the raw OCR text, so an unreadable hora renders as a blank cell instead of a plausible-looking fake value; a page whose registro count diverges from `registro_parser.verificar_contagem_posicoes` is tracked in `self._avisos_contagem` and surfaced through a dedicated "Avisos de contagem" button (same pattern as "Erros de página"). **Fase 24a**: `_processar_uma_pagina` and `_adicionar_registros`/`_revisao_confirmar` no longer CONTAIN this logic — they're thin wrappers that call `pipeline.processar_uma_pagina`/`pipeline.montar_registro_exportacao`/`validacao.confirmacao.confirmar_revisao_manual` and then update widgets/counters/navigation from the result. `_processar_uma_pagina` stays a method (not a free function) specifically because `teste_worker_imagem_falha.py` patches it via `patch.object(App, '_processar_uma_pagina', ...)`.

**Fase 6 — ROI/template da folha (experimento AVALIADO E DESCARTADO — o código não está no repositório)**: ⚠️ leia primeiro o parágrafo "Estado atual" no fim desta seção. O que segue descreve o que o experimento fez e o que ele mediu, não código que exista hoje. `parsing/roi.py` derived a Region of Interest from the sheet's known printed header (via the header row already located by `_detectar_linha_cabecalho` in a first OCR pass — not fixed pixel coordinates, which real photos proved unusable: rotation/zoom/framing vary wildly between shots of the same physical form). `localizar_roi_tabela(resultado, largura, altura)` returns a bounding rect spanning the header's real top to the last detected registro's real bottom, with margin proportional to local line height — or `None` when there's no real anchor (no header, or header with zero registros), never inventing a rectangle. `extrair_com_roi(imagem_processada, ocr_engine)` orchestrates a first full-page OCR pass (reused as the anchor) and, only when a ROI is found, a second OCR pass on the crop — both via the existing unmodified `OCREngine`/`parse_registros`. `_resultado_roi_e_confiavel` is a deliberately conservative accept policy: same registro count + header re-detected in the ROI pass; it never uses CONFIRMADO/REVISAO counts (out of this module's scope by design, and explicitly vetoed as a superiority signal).
  **Empirical result (3 real photos, 24 matrículas compared field-by-field against the photos): 2/3 photos identical between baseline and ROI; 1/3 (`20260808_144413.jpg`, last row) had the ROI pass silently substitute a WRONG digit (`21491`→`21691`) that the accept policy did not catch — same registro count, header still detected. Cost was +65–80% OCR time per page (46–50s added on top of ~65–70s baseline).** This is a genuine, reproducible correctness regression, not a hypothetical one — per this phase's explicit mandate ("não force a adoção como caminho principal" without demonstrated gain), ROI was never wired into the app: `_processar_uma_pagina` calls `ocr_engine.recognize` + `parse_registros` directly, unchanged.
  **Estado atual (verificado): `parsing/roi.py` e `teste/teste_roi.py` NÃO existem e NUNCA foram versionados** — `git log --all -- "*roi*"` não devolve nada, e o único vestígio no disco é um `parsing/__pycache__/roi.cpython-310.pyc` órfão, de quando o arquivo existiu localmente durante o experimento. Este parágrafo corrige a redação anterior desta seção, que afirmava que o módulo continuava "fully implemented and unit-tested but dormant"; não há código dormente para reativar. O que sobrevive da Fase 6 é a MEDIÇÃO acima, e é para isso que ela serve: uma nova tentativa de ROI começa do zero e só se justifica com uma política de aceitação mais forte (cruzar texto/confiança campo a campo entre as duas passadas, não só contagens estruturais) e uma amostra de fotos reais bem maior — sabendo de antemão que o custo é +65–80% de tempo de OCR por página.

**Fase 7 — preparação para operação real (lote de ~50 folhas)**: hardening of `ui/app.py` only — no business rule, OCR, parser, or ROI change. Three risk areas found and fixed:
  - **Seleção múltipla de imagens**: `_on_selecionar_imagem` now uses `askopenfilenames` (plural). A single file keeps the exact old code path (`_worker_imagem`, unchanged, still covered by `teste_worker_imagem_falha.py`); multiple files go through the new `_worker_imagens(caminhos)`, which mirrors `_worker_pdf`'s per-page isolation — a file that fails to open or fails anywhere in `_processar_uma_pagina` becomes one ERRO row and the batch continues, never aborts on one bad photo. This closes the real operational risk of manually repeating a single-file dialog ~50 times.
  - **Progresso do lote**: a `("total", n)` queue message (sent by `_worker_pdf` right after `contar_paginas` and by `_worker_imagens` at start) feeds `self._total_paginas_lote`; `_atualizar_status` shows `Página X/Y` during a running batch instead of only a running count with no denominator. An hour-long batch with zero progress signal is a real risk of the operator killing the app out of uncertainty, losing everything (nothing is persisted until "Gerar planilha").
  - **PROBLEMAS C/D/E da revisão manual (segurança contra falso CONFIRMADO)**: `_confirmar` (inside `_abrir_revisao`) no longer force-sets `CONFIRMADO` just because the button was clicked. It rebuilds a synthetic `Registro` from the edited fields (confidence 1.0 — human-verified, not an invented value) plus the record's already-resolved data/hora, re-runs the existing `validacao.classificar_registro` unchanged, and only removes the row from the pending list if the result is genuinely `CONFIRMADO` — otherwise it stays visible with the fresh `observacao` explaining what's still missing (e.g., DATA, which this dialog can't edit). It also re-queries `DataManager.buscar_colaborador` with the corrected matrícula so Nome/Setor/Cargo stop showing `"(não encontrado)"` after a correction that actually resolves. `_abrir_revisao`'s `pendentes` filter changed from `status != "CONFIRMADO"` to `status == "REVISAO"`: ERRO rows (whole-page failures, no real field data) can no longer be listed there — there's nothing genuine to correct field-by-field, and letting an operator type values into an ERRO row would be inventing data from nothing. This also fixes the counter desync (`_contador_revisao` never counted ERRO rows, so "confirming" one used to decrement it incorrectly).
  New test: `teste/teste_lote_operacional.py` — 50 synthetic pages (mocked OCR, 3 deliberately corrupted files interspersed) verifying no page is lost, corrupted files isolate cleanly, page numbering has no gaps/dupes, and the final XLSX is structurally consistent at that scale. `teste_ui_integracao.py`'s revisão section was updated (not just to "make it pass"): it used to force-confirm blindly, which is exactly the unsafe behavior this phase removes, so it now substitutes a small deterministic fake `DataManager` for that step (real local `dados/` content shouldn't decide whether a test passes) and explicitly covers the C/D/E scenarios (real fix → CONFIRMADO with Nome/Setor updated; unresolved fix → stays REVISAO; an ERRO row never appears in the dialog).

**Fase 9 — recuperação contextual de OCR e redução segura de REVISAO**: `dados/Motivos.xlsx` passou a ser uma **lista fechada de 7 motivos** (`HORÁRIO NEGADO`, `RH`, `ADM`, `ARMÁRIOS`, `FOLGA FIXA`, `ESQUECEU CRACHÁ`, `TREINAMENTO`) — os sinônimos `NEGADO`/`NEGADA`/`H. NEGADO` saíram da base, e com eles quebrou a comparação de texto INTEIRO que a Fase 1 usava: o que a folha traz é quase sempre a abreviação curta ("Negade", "H.v. vigaolo") contra um candidato longo, e a similaridade despencava por diferença de TAMANHO, não por falta de evidência. Cinco recuperações foram acrescentadas, todas contextuais e todas com o mesmo padrão de evidência já usado em `recuperacao_matricula.py` (gerar leituras plausíveis por tabela FECHADA de confusões de OCR → perguntar à base/ao contexto quais existem → uma só existe = aceita, duas = ambíguo = REVISAO):
  - **MOTIVO — reconhecimento estrutural da família "negado"** (`validacao/correspondencia_aproximada.avaliar_evidencia_familia_negado`): em vez de baixar o limiar global (o que afrouxaria também RH/ADM/ARMÁRIOS/...), quebra o texto em tokens, procura o token que carrega o NÚCLEO (`NEGADO`/`NEGADA`) — o "H."/"H.V." é a abreviação de "horário" e vira evidência auxiliar, não o alvo —, desfaz confusões conhecidas (dígito lido no lugar de letra: `NE6400`=NEGADO; n/v/w/m cursivos: `vigado`/`Wegado`/`Migado`; "d" quebrado em "ol"/"cl": `Negaola`/`vigaolo`) e exige **evidência combinada**: similaridade ≥ `LIMIAR_FAMILIA_FORTE` (0.75) sozinha, OU ≥ `LIMIAR_FAMILIA_COMBINADO` (0.60) mais um segundo critério independente (o esqueleto de consoantes N-G-D, ou a abreviação de "horário"). Em qualquer caso ainda tem de ganhar por `MARGEM_SOBRE_OUTROS_MOTIVOS` da melhor similaridade contra os motivos de FORA da família — é essa checagem que impede os outros 6 motivos de serem absorvidos. Limiares calibrados contra os textos reais das fotos E contra controles negativos (os outros motivos e suas deformações, nomes de gestor, texto impresso do formulário): o pior controle negativo pontua 0.615 sem critério secundário, abaixo de qualquer combinação aceita.
  - **RESPONSÁVEL — leitura do código GR** (`_ler_codigo_gestor`): quando o gestor é anotado pelo código, o que vem depois costuma ser o nome de quem estava na portaria, ilegível no OCR ("GRS- Lmone"), e afundava a similaridade do texto inteiro. O código é lido por tabela fechada (`S`→`5`; `I`/`L`/`1` entre si) e confirmado contra a base. Roda **depois** das tentativas de match exato/prefixo (a identificação mais específica, `"GR<n> - <NOME DO GESTOR>"` inteira, sempre ganha do código nu) e **antes** da aproximação do texto inteiro. `GRI` continua AMBIGUA (GR1 e GRL existem os dois). Isto mudou uma decisão da fase anterior: `GRS` sozinho, que era tratado como ambíguo por pura similaridade de texto, agora resolve para `GR5` — `S` é leitura conhecida de `5` e não de `L`, e GR5 é a única leitura que existe na base (ver comentário em `teste_gestor_sem_expansao_unica_nao_e_chutado`).
  - **DATA — contexto do lote** (`parsing/contexto_lote.py`, módulo novo): o OCR entrega a data sem ano ("23.04") quando o ano foi escrito pequeno ou cortado na foto. `interpretar_data` continua recusando esse texto — sozinho ele não permite determinar o ano. Mas o ano está escrito nas OUTRAS folhas do mesmo lote: `ContextoLote` acumula só as datas interpretáveis POR COMPLETO (data recuperada por contexto nunca realimenta o contexto) e elege um ano quando ele é predominante com folga (`MAXIMO_DATAS_DIVERGENTES`=2 e `FATOR_PREDOMINANCIA`=3× — as duas condições juntas separam "um ou dois anos lidos errado no meio de dezenas iguais" de "lote que atravessa a virada do ano", que não pode eleger ano nenhum). `ano_divergente_do_lote` é o caminho inverso e igualmente conservador: uma data cujo ano ESTÁ escrito mas destoa do lote (real: "28/04/20" entre trinta datas de 2026) vai para REVISAO — o ano não é reescrito, só se reconhece que não pode ser confirmado sozinho. O contexto é propriedade da `App` (`self._contexto_lote`), alimentado com a página inteira antes de classificar suas linhas, e zerado junto com "Limpar resultados". `classificar_registro(..., contexto_lote=...)` é opcional: sem ele o comportamento é exatamente o anterior.
  - **DATA — formato deformado** (`_partes_de_data_deformada`): último recurso para o separador que o OCR multiplicou/moveu ("14.0.4.26"). Condições estreitas de propósito: só dígitos e separadores de data (sem letras/espaço, então uma caixa data+hora não entra aqui), ao menos um separador, e exatamente 6 ou 8 dígitos. Nenhum dígito é inventado — só se ignora onde os separadores caíram, e o resultado ainda passa pela validação de calendário.
  - **HORA** — o espaço entrou na classe de separadores de HORA:MINUTO ("07 53"), com âncora `^...$` no filtro de coluna correspondente em `registro_parser._PARECE_HORA` para que uma frase impressa com dois números soltos não volte a passar; o separador dos SEGUNDOS **não** ganhou o espaço (faria "23 04 26", uma data, virar 23:04:26). `recuperar_hora` trata a hora colada a outro texto na mesma caixa ("12:55 Miguel") — exatamente um trecho com forma de hora, nenhum dígito sobrando fora dele, e ainda passando por `interpretar_hora`. E `tentar_separar_data_hora_mesclada` passou a devolver `(data, None)` quando a caixa mesclada tinha mesmo um trecho de hora só que impossível ("14.04 -26 90:24"): a DATA legível não pode ser perdida por causa da HORA, que é o campo opcional.
  Efeito colateral que a fase teve de fechar: **MOTIVO e RESPONSÁVEL ausentes agora bloqueiam o CONFIRMADO**. Antes uma coluna vazia simplesmente não entrava na avaliação, e o registro saía CONFIRMADO com a célula em branco — indistinguível de "confirmadamente vazio". Isso só ficou visível quando as normalizações de motivo deixaram de barrar essas linhas antes (duas folhas reais caíram exatamente nesse caso). `teste_validacao.py` teve o helper `_reg` estendido para injetar motivo/responsável preenchidos por padrão, pelo mesmo motivo que ele já injetava data/hora válidas: isolar a condição que cada teste realmente testa.
  Novo teste: `teste/teste_recuperacao_contextual.py` (19 blocos, sem OCR e sem as planilhas reais). Resultado medido nas 5 fotos reais (mesmo OCR, cache do PaddleOCR reaproveitado): 40 registros, 8 por página, ordem física e identidade linha a linha idênticas ao baseline; **3 → 19 CONFIRMADO, 37 → 21 REVISAO, 0 ERRO**. Nenhuma matrícula com caractere não numérico, nenhuma data fora de `DD/MM/AA`, nenhuma hora fora de `HH:MM`, nenhum CONFIRMADO com motivo fora da lista fechada. Atenção ao comparar com números antigos: o baseline citado no pedido da fase (16/24) foi medido com a `Motivos.xlsx` ANTIGA; com a lista fechada já em `dados/`, o baseline real do código anterior era 3/37.
  **Limitações residuais desta fase** (o que continua em REVISAO, e por quê — todos são "falta de evidência", não bug):
  - **Responsável cortado/ilegível** é o maior grupo (10 das 21 linhas reais): nome cortado na foto, código GR com letra que não é código nenhum, rabisco. Por projeto, não se escolhe o candidato "mais parecido" — `MARGEM_AMBIGUIDADE_PADRAO` e a checagem de leitura única continuam valendo.
  - **Motivo com evidência de critério único**: leituras como `Nebano` e `NoGAAO` ficam acima do limiar combinado mas sem o esqueleto N-G-D nem a abreviação de "horário". São provavelmente HORÁRIO NEGADO, mas com um só critério — preferiu-se REVISAO.
  - **Ano divergente** não é reescrito, só sinalizado: a linha vai para REVISAO com o ano que está escrito. Se um lote real tiver MUITAS datas com o ano mal lido, `MAXIMO_DATAS_DIVERGENTES` desliga o contexto inteiro e as datas sem ano voltam a REVISAO — falha segura, mas perde a recuperação.
  - **O contexto do lote é sequencial**: uma folha sem ano processada antes de existirem 3 datas completas no lote não é recuperada. Nas fotos reais isso não ocorre (a folha sem ano é a última), mas numa remessa em que a primeira folha esteja assim, ela ficará em REVISAO.
  - Continua valendo a limitação da Fase 1: MOTIVO/RESPONSÁVEL não têm filtro de formato, então um fragmento de texto impresso ainda pode cair nessas colunas (não observado nesta rodada).

**Fase 12 — segurança da confirmação e detecção de CAMPO PERDIDO**: a medição da Fase 11 auditou os 20 CONFIRMADO automáticos contra as fotos e achou 2 com defeito, ambos na HORA. O grave é o da matrícula **26319**: a folha tem `07:49` escrito e legível, e o registro saiu **CONFIRMADO com a coluna Hora vazia**. Olhando o parser, o dado não estava ausente — estava perdido:
```
L2: data='14.0.4.26'  hora=AUSENTE  matricula='26319' ...
      nao_associados: ['07:4', 'tiago', 'Clubi Prot.']   <- a hora, lida e descartada
```
  O OCR cortou o último dígito (`07:49`→`07:4`) e o filtro de formato da coluna HORA (`_PARECE_HORA`, que exige dois dígitos após o separador) recusou o elemento — corretamente, do ponto de vista dele, que existe para impedir texto impresso de virar dado. O elemento não sumiu: foi para `nao_associados`. **É essa sobra que passou a ser lida como evidência.**
  - **`validacao/integridade.py`** (módulo novo) separa os dois motivos pelos quais um campo chega vazio à validação: *a folha não tinha* × *o OCR leu e o parser não associou*. `detectar_campo_perdido(registro, campo)` varre o `nao_associados` da própria linha procurando um fragmento cujo FORMATO só faça sentido para o campo que faltou, e devolve o texto suspeito (ou `None`). É evidência de **captura**, não de conteúdo: o módulo nunca diz qual é o valor, só que havia algo com a cara dele e que se perdeu — quem decide continua sendo uma pessoa, na revisão.
  - Só há teste de formato para **hora / data / matrícula** (`CAMPOS_COM_EVIDENCIA_DE_FORMATO`). MOTIVO e RESPONSÁVEL são texto livre: qualquer sobra da linha (nome, setor) "pareceria" um deles e geraria evidência falsa — e os dois já bloqueiam quando ausentes, então não há lacuna. Detalhes que evitam falso positivo: um fragmento de 4 dígitos colados só vale como hora se formar uma hora POSSÍVEL (`1108`→11:08 sim; a matrícula `3875`→38:75 não), e as anotações que o próprio pipeline acrescenta a `nao_associados` (`"[data/hora mescladas no OCR: ...]"`, entre colchetes) são ignoradas — elas contêm data e hora e fariam o detector disparar sozinho.
  - **A regra da HORA não mudou**: ela continua opcional. A única checagem bloqueante nova é `hora vazia` **E** `há evidência de perda na linha` → REVISAO com `descrever_perda`, que nomeia o campo e mostra o texto lido. Hora genuinamente ausente ou ilegível continua confirmando como antes. Vem depois das checagens de matrícula/data de propósito: quando o registro já vai para REVISAO por algo mais grave, é esse motivo que o operador precisa ler primeiro.
  - Para os campos que **já** bloqueavam (matrícula, data), a mensagem passou a carregar o texto perdido (`_com_evidencia_de_perda`): "matrícula não identificada pelo OCR (possível perda de captura: o OCR leu `'28972 tente de Lga'` nesta linha)". O bloqueio é o mesmo; o que muda é o operador saber que o dado ESTÁ na folha e onde procurar.
  - **A revisão manual não vira porta dos fundos**: `_revisao_confirmar` reconstrói o `Registro` sintético **com o `nao_associados` original**, preservado no dict de exportação sob `ocr_nao_associados` (chave técnica; o `xlsx_exporter` itera sobre as suas próprias `COLUNAS` com `.get()` e a ignora). Sem isso bastava abrir a revisão e clicar em confirmar para reverter o bloqueio. Não prende o operador: a checagem só dispara se o campo continuar VAZIO — digitou a hora que está no papel, confirma.

**Fase 14 — robustez e desempenho do PDF**: fase de investigação primeiro, implementação depois. A medição usou o PDF real de 5 páginas e um PDF sintético de 50 (as mesmas 5 folhas repetidas 10×, só para ver tendência de memória — nunca para medir precisão), isolando a camada de PDF da camada de OCR.
  - **Processamento incremental: já estava correto — nada foi alterado.** Em 50 páginas a memória do `pdf_reader` **estabiliza em ~322 MB** (`+0,18 MB/página`, com platô a partir da 5ª página) e o tempo é constante em `147 ms/página`. Ou seja, o crescimento de `~33 MB/página` medido na Fase 11 **não vem desta camada** — vem do OCR, e fica para a Fase 19. Não se mexeu no gerador para "otimizar" o que a medição mostrou já funcionar.
  - **Retenção durante o `yield` (corrigido, `ocr/pdf_reader.py`)**: um gerador fica *pausado* no `yield` enquanto quem consome trabalha — e aqui quem consome roda o OCR da página, dezenas de segundos. Inspecionando `gi_frame.f_locals` com o gerador pausado, mediu-se **26,4 MB vivos por página**: `pixmap` (8,8 MB), `imagem_rgb` (view sobre o buffer do pixmap, que o mantém vivo) e `imagem_bgr` (a cópia entregue). Soltar `pixmap`/`imagem_rgb`/`pagina` antes do `yield` (e `imagem_bgr` depois dele) baixou para **8,8 MB** — o que resta é a própria imagem que o consumidor está usando. Pico do lote de 50 páginas: `387 → 370 MB`. Nenhuma mudança de resultado: `imagem_bgr` sempre foi uma cópia própria, não uma view.
  - **Rastreabilidade (corrigido, `ui/app.py`)**: coexistem DOIS números de página — `_proximo_numero_pagina` (posição da folha no lote, o que vai para a coluna Página e preserva a ordem física) e `PaginaPdf.numero` (posição dentro daquele arquivo). Eles só coincidem quando o PDF é a primeira coisa da sessão. A mensagem de erro citava apenas o número interno, então o operador via *"Falha ao renderizar página 3"* numa linha rotulada *"página 8"*, sem saber qual folha conferir. Agora a origem sai nomeada e completa (`"página 3 de 'mes.pdf'"`), e o mesmo prefixo passou a acompanhar também as falhas de OCR/parser da página, não só as de renderização.
  - **Isolamento de falhas: já correto, agora coberto por teste.** O gerador devolve todas as páginas, marca só a que falhou (`imagem=None`, `erro` preservado sem ser engolido), não abre furo na numeração e continua o lote. Falhas de documento inteiro (arquivo ausente, arquivo que não é PDF) continuam levantando exceção, como devem.
  - **Achados registrados, sem correção (fora do escopo desta fase)**: (1) o PyMuPDF **é resiliente demais para que o caminho de erro por página seja exercitado na prática** — uma imagem embutida destruída resulta numa **página em branco sem exceção nenhuma**, que segue como página "bem-sucedida" com ZERO registros; isso não gera CONFIRMADO algum (não há linha) e é sinalizado pelo aviso de contagem (`esperava 8 posições, foram reconhecidas 0`), mas não vira linha de ERRO; (2) um PDF **truncado é recuperado** pelo PyMuPDF, que reconstrói as páginas que consegue em vez de falhar. Os dois comportamentos estão travados em teste para que uma troca de versão do PyMuPDF não os altere despercebidamente.
  - **Nenhum ganho de tempo é reivindicado**: a renderização é `0,5%` do tempo total (o OCR é `97%`), então a correção de memória não muda o relógio. Resultado nas 5 folhas reais: **40 registros, 19 CONFIRMADO, 21 REVISAO — zero diferença campo a campo** contra a execução anterior, ordem física idêntica, XLSX validada.
  Novo teste: `teste/teste_pdf_robustez.py` (8 blocos, PDFs sintéticos, sem OCR).

**Fase 15 — interpretação estrutural da folha (investigada e DESCARTADA — nenhuma alteração de código)**: a hipótese era que a geometria já devolvida pelo OCR (`OCRResult.box` = `[x1,y1,x2,y2]`) pudesse melhorar a associação entre linhas, colunas e campos. A medição, sobre as mesmas 5 folhas reais (40 liberações, 200 posições de campo), mostrou que **a associação espacial já está correta e não é o que limita a extração** — por isso nada foi implementado.
  - **A associação acerta 190 das 200 posições de campo (95%)**, com 40/40 registros, 8 por página, ordem física preservada, zero perda e zero duplicação.
  - **Caixas que abrangem duas colunas: 35 de 276 elementos (12,7%)** — e praticamente todas são o par DATA+HORA colado numa caixa só, artefato que `tempo_parser.tentar_separar_data_hora_mesclada` **já resolve** desde a Fase 1. Não é problema aberto.
  - **O teste decisivo** foi, para cada um dos 10 campos ausentes, verificar se existia um elemento não associado posicionado *dentro* da coluna daquele campo (corte de associação ≈ 500–547 px por página). Resultado: 3 não tinham sobra nenhuma na posição; **4 tinham a sobra a 34, 36, 98 e 124 px do centro da coluna** — ou seja, geometricamente perfeitas — e foram recusadas **pelo filtro de FORMATO** (`_PARECE_DATA`/`_PARECE_HORA`), não pela geometria: `'13104126'` (a data `13|04|26`, com as barras lidas como `1`, sem separador reconhecível) e `'07:4'`, `'11:0s Card'`, `'1108 fernamenta'` (horas truncadas ou com dígito lido como letra). Mexer nisso seria afrouxar um filtro de CONTEÚDO — fora do escopo desta fase, e é justamente o filtro que a Fase 1 criou para impedir texto impresso de virar dado.
  - **2 dos casos restantes seriam ERRO se associados**: a sobra bem posicionada é o texto do SETOR (`'Diposito'`, `'Manuleneas'`) numa linha cuja célula de matrícula está **genuinamente em branco no papel** (verificado na foto). Associar por proximidade ali inventaria uma matrícula a partir do setor — exatamente o que o invariante do projeto proíbe. O comportamento atual está certo.
  - **Sobrou 1 caso real** (`'28972 tente de Lga'`, matrícula colada ao setor numa única caixa de OCR, a 250 px da coluna). Mas **ele não é reproduzível**: comparando duas execuções independentes do OCR sobre as mesmas imagens, só **4 dos 11** problemas estruturais se repetem — e os 4 estáveis são justamente os 2 de filtro de formato e os 2 de célula vazia no papel. **Nenhum problema estável é de associação espacial.** Uma lógica geométrica calibrada contra os 7 instáveis miraria ruído de segmentação do detector, e qualquer "ganho" medido seria artefato da execução escolhida.
  - **Decisão**: não adotar. O teto desta fase seria 1 registro em 40, num caso que aparece e desaparece entre execuções, ao custo de mexer no núcleo do parser espacial — que hoje sustenta 190/200 campos e 40/40 registros. Pelo critério da própria fase ("se não houver melhoria estrutural mensurável, não adotar"), a evidência manda não implementar. Revisitar só se surgir um lote real em que a associação erre de forma **estável e reproduzível**; o roteiro de medição está descrito acima e pode ser repetido tal e qual.

**Fase 16 — consistência contextual (investigada e DESCARTADA para confirmação automática — nenhuma alteração de código)**: a hipótese era que outras linhas da MESMA FOLHA e do MESMO LOTE pudessem servir de evidência para reduzir `REVISAO` ou detectar inconsistências. Medida sobre as mesmas 5 folhas reais (40 liberações), com o OCR executado **uma vez** e mantido em cache, de modo que o uso de contexto fosse a única variável entre as variantes. Baseline reproduzido exatamente: 40 registros, 19 CONFIRMADO, 21 REVISAO, 0 ERRO. Relatório completo em `saida/medicao_fase16_contexto.md` (fora do versionamento — cita nomes reais de gestores). **Nenhum mecanismo automático foi adotado**, por medição, não por precaução:
  - **RESPONSÁVEL — reduzir candidatos por contexto não pode funcionar, e não é neutro.** As 11 falhas de responsável são **todas `SEM_CORRESPONDENCIA`, nenhuma `AMBIGUA`** — e isso decide a questão por construção: reduzir candidatos remove concorrentes, o que pode aumentar a *margem* entre 1º e 2º, mas nunca eleva a *similaridade do melhor*, que é justamente o que o limiar barra. Confirmado empiricamente nos três escopos (base 21 / lote 7 / folha 2–4): os 11 continuam `SEM_CORRESPONDENCIA`. Pior, restringir os candidatos **destruiu 9 confirmações corretas** (19 → 10 CONFIRMADO em ambos os escopos, recuperando 0). A causa é concreta e vale conhecer: a base cadastra os códigos nus (`GR1`…`GRL`) além das identificações completas, esses códigos **nunca aparecem como gestor "resolvido"** (sempre expandem para a forma específica), logo o contexto não os contém — e tirá-los da lista quebra `_ler_codigo_gestor` e a expansão de prefixo da Fase 9, que dependem de o código existir na base. **Contexto, aqui, não é um subconjunto seguro da base.**
  - **A sugestão contextual erra metade das vezes.** Contra a verdade lida NAS FOTOS, o top-1 por similaridade dentro do conjunto do lote acerta **4 de 8** casos com resposta possível. O caso decisivo: três linhas da folha 4 são a mesma rubrica cursiva, o gestor certo **está** no conjunto do lote, e a similaridade o coloca em 6º, 4º e **último** lugar de 7 — nesses casos o ranking contextual é anticorrelacionado com a verdade. Virasse confirmação automática, o lote ganharia 4 linhas certas e **7 linhas ERRADAS confirmadas**.
  - **DATA completada pela folha: a métrica melhora enquanto o resultado piora.** Completar a data ausente com a predominante da folha leva 19 → 21 CONFIRMADO, **e as duas novas estão erradas**. Em p1L1 a folha é unânime em `14/04/26` (7/7) e **a foto mostra `13/04/26`** — o OCR até leu o campo (`'13104126'`, barras lidas como o dígito `1`), e a regra escreveria uma data errada marcada CONFIRMADO, em silêncio. Em p3L3 não há sobra com dígito nenhum na linha: o valor viria inteiramente dos vizinhos, invenção pura. Detalhe que fecha o argumento: a própria folha **contradiz** a frequência — com `13/04` em L1 a folha fica cronologicamente ordenada; com o `14/04` que a regra escreveria, ela começaria às 18:59 e cairia para 07:53 na linha seguinte.
  - **Detecção de inconsistência: correta, e sem nada novo para detectar.** Duas regras medidas. Por frequência ("data que destoa da predominante da folha"): sinaliza 4 linhas, **as 4 já em REVISAO** por outro motivo, e produz 1 falso alarme (uma data legítima de virada de dia). Por **ordem cronológica** da folha (a folha é preenchida de cima para baixo): **28 de 31 pares consecutivos (90%) são monotônicos**, e as 3 violações são exatamente os 3 defeitos de data reais, com **zero falsos positivos** — é o melhor sinal contextual encontrado na fase, mas as 3 **também já estão em REVISAO**, então a mudança líquida é igualmente **0**.
  - **MATRÍCULA por vizinhança no lote reproduz um modo de falha já medido**: as vizinhas mais próximas são `28977`→`28972` e `19545`→`19548`/`19547` (0,80), **exatamente** as substituições que a Fase 13 mediu como falso CONFIRMADO a 1800 px. HORA: o contexto estreita a faixa (`'07:4'` entre horas `07:5x`) mas não escolhe o dígito — restam 10 leituras. MOTIVO: 36 das 40 linhas são `HORÁRIO NEGADO`, predominância que é justamente o caso em que decidir por frequência absorveria os 4 motivos restantes.
  - **Decisão**: não adotar nenhum mecanismo automático. Contra o critério da própria fase — redução real de revisões corretas (**não**: 0 das 11 recuperáveis, e as 2 datas "recuperadas" estão erradas), zero novo falso CONFIRMADO (só satisfeito não adotando), detecção melhor de inconsistências (o sinal cronológico é limpo mas muda 0 linhas), benefício reproduzível (não há benefício a reproduzir) — a evidência manda não implementar.
  - **O que sobrevive para as Fases 17/18 (CASO B — sugestão, nunca confirmação)**: a evidência contextual existe e é apresentável, só não é decisiva. Três sinais medidos merecem ser MOSTRADOS na revisão sem nunca confirmar: (1) "o lote usa 7 destes 21 gestores", que encurta a lista do `Combobox` sem escolher por ninguém; (2) o sinal cronológico acima, como destaque "esta linha quebra a ordem da folha"; (3) "estas N linhas parecem ter a mesma rubrica", que deixa resolver várias de uma vez. Note-se que (1) e (3) são exatamente as evidências que, viradas decisão automática, produziram os 7 falsos CONFIRMADO — a diferença entre sugerir e confirmar não é de grau. **Revisitar só com um lote real em que o mesmo responsável apareça bem lido numa folha e mal lido em outra**, e ainda assim exigindo evidência independente da similaridade (código legível, leitura única na base), como já fazem `recuperacao_matricula.py` e `_ler_codigo_gestor` — nunca similaridade nem frequência sozinhas. A causa dominante continua fora do alcance do software: 6 dos 11 casos de responsável são a coluna saindo do enquadramento da foto (as caixas do OCR terminam em `x2 = 2339`, a largura exata da imagem).

**Diagnóstico — qualidade de captura e detecção de enquadramento (investigado, SEM implementação; não é uma fase do roadmap)**: pergunta levantada pelas Fases 15/16 — o sistema consegue detectar sozinho que a folha está cortada à direita? Medido sobre as mesmas 5 folhas reais, **reaproveitando o OCR em cache** (nenhuma passada nova, nenhum recorte, resolução intocada) e comparando sempre contra a largura/altura **reais da imagem processada** com tolerância relativa (`0,2%` de `W`) — nunca contra o número `2339`, que é só o valor atual de `LADO_MAXIMO_PADRAO`. Relatório completo em `saida/diagnostico_captura.md` (fora do versionamento). **Conclusão: CASO B — o sinal é real e barato, mas não é validável com a amostra existente; nada foi implementado.**
  - **O achado que reformula a pergunta**: a folga entre o texto mais à direita e a borda é de **0–1 px nas 5 folhas**, e a borda do PAPEL não aparece em nenhuma. Isto separa duas perguntas que estavam coladas: *"a folha não está inteira na imagem"* é verdade em **5 de 5**; *"o corte fez PERDER dado"*, em **2 de 5** (as 6 falhas de captura são as 3 últimas linhas de duas folhas). Ou seja, **a amostra tem 5 positivos e 0 negativos** para a primeira pergunta — a taxa de falso positivo, que o critério de segurança exige medir, é **inmensurável** aqui: qualquer regra que dispare sempre marca 5/5 e parece perfeita.
  - **Sinais medidos**: "alguma caixa encosta na borda direita" dispara em 5/5 (precisão 40% contra a perda real de dado); o rodapé impresso não serve de âncora (o OCR só o localizou em 2 das 5 folhas); a âncora utilizável é o **rótulo impresso da coluna mais à direita**, comparado por prefixo contra o texto fixo do formulário — lido a 100%/93%/64%/71%/46% nas 5 folhas, e **reprodutível** (4 de 5 idênticas entre duas execuções independentes de OCR, 1 com ±1 caractere). Por linha, "o elemento do responsável encosta na borda" pega **6 de 6** casos de captura mas dispara 24 vezes em 40 linhas — **25% de precisão**.
  - **Por que não se adota**: o sinal detecta **corte**, não **dano**, e as duas coisas se descolam justamente na folha mais cortada da amostra — nela o corte removeu o sufixo com o nome do auxiliar de portaria, que `resolver_responsavel` **já descarta por projeto**, deixando o código do gestor intacto e zero falhas. É um falso positivo **estrutural**, não ruído. As regras que o evitariam dependem de limiares (25% do rótulo, metade das linhas) **ajustados olhando estas mesmas 5 fotos**, sem conjunto de validação independente — exatamente o que o critério de segurança proíbe. E uma regra que dispararia em 5 de 5 folhas reais não é aviso, é ruído constante.
  - **Custo, se um dia for implementado**: `0,018 ms/página` e `1,5 KB` de pico, sobre caixas já em memória — ~10⁻⁶ do tempo do pipeline (o OCR são ~40 s/página). O custo nunca será o obstáculo; o obstáculo é a validação.
  - **Insumo registrado para uma fase futura (não cria fase nova)**: se a questão voltar, o caminho medido é **âncora de conteúdo, não limiar de pixel** (prefixo do rótulo impresso + caixa encostando na borda real daquela imagem), a intervenção máxima justificável pelos dados é **informativa** (um aviso na aba "Avisos" que já existe — nunca bloqueio, nunca alteração de dado, nunca influência sobre `CONFIRMADO`), e **o que falta para decidir é amostra**: um lote real com capturas COMPLETAS (borda do papel visível), sem o qual qualquer número de precisão é ficção. A correção mais barata continua fora do software: fotografar a folha com margem à direita.

**Fase 17 — Motor de evidências (ADOTADO — CASO A)**: camada explícita que registra POR QUE cada valor foi aceito, corrigido, recusado ou mandado para REVISAO. É **observacional**: nenhuma decisão consulta o dossiê, e a regressão nas 5 folhas reais confirmou **40 registros, 19 CONFIRMADO, 21 REVISAO, 0 ERRO, zero diferença campo a campo** contra a baseline das Fases 13–16.
  - **O problema não era falta de informação, era descarte.** O mapeamento sobre as 40 liberações reais (com o OCR em cache, sem passada nova) mediu o que o pipeline PRODUZ e JOGA FORA a cada execução: o **2º melhor candidato de motivo (40/40)**, a **posição/caixa de cada campo (38/40)**, a **similaridade numérica do responsável (37/40)** e a **confiança do OCR da matrícula nos CONFIRMADO (19/40)**. O que sobrevivia era a `observacao` — uma frase pronta em português, boa para o operador ler e imprestável para outra camada raciocinar em cima.
  - **`validacao/evidencias.py`** (módulo novo, desacoplado) só DESCREVE evidência e não decide nada — mesmo espírito de `validacao/integridade.py`. `Evidencia` é uma dataclass **imutável** com `campo`/`tipo`/`origem`/`resultado`/`motivo`/`valor_observado`/`valor_relacionado`; `DossieRegistro` acumula na **ordem de observação** (a ordem É a cadeia de raciocínio: o que o OCR leu → como foi normalizado → o que a base respondeu → que regra decidiu; reordenar por campo ou por peso destruiria isso). Os 8 tipos do escopo são todos emitidos de verdade — medido no lote real: `ocr_bruto` 195, `posicao` 195, `correspondencia_base` 118, `regra` 117, `normalizacao` 36, `contexto` 8, `ausencia` 5, `conflito` 2 (média de **16,9 evidências por registro**).
  - **DELIBERADAMENTE NÃO EXISTE SCORE.** Nenhuma nota 0–100, nenhuma soma ponderada. Um número desses apagaria a distinção entre "não há evidência" e "há evidência contrária" — que é exatamente a distinção que a Fase 12 precisou criar para não confirmar registro com campo perdido. Os fatores ficam LISTADOS lado a lado (`FAVORAVEL`/`DUVIDA`/`NEUTRO`), e `resumo_por_campo` devolve **contagem**, não pontuação. `sem_evidencia(campo)` é True só quando o motor não olhou para o campo — diferente de uma evidência `ausencia` (olhou, não havia nada) e diferente de uma `DUVIDA` (olhou, o que viu é suspeito). Os três estados são testados separadamente.

**Fase 19 — Performance avançada (CASO B — uma adoção de memória; nenhum ganho de tempo passou no critério)**: baseline remedida **no estado atual** (já com Fases 17 e 18), mediana de 3 repetições sobre as mesmas 5 folhas reais. Relatório em `saida/medicao_fase19_performance.md` (fora do versionamento). Alteração adotada: **1 arquivo, −29,8 MB de retenção**; baseline funcional **idêntica** (40/19/21/0, zero diferença campo a campo, zero dossiê diferente, XLSX íntegra, suíte 20/20).
  - **Baseline atual**: total `182,80 s` para 5 folhas (`36,56 s/página`), variação de 1,1% entre repetições. **OCR = 178,99 s = 97,9%**; pré-processamento `3,50 s` = 1,9% (do qual `fastNlMeansDenoising` sozinho é 97,2%); leitura 0,1%; miniatura 0,03%; **validação, já incluindo montar os 40 dossiês da Fase 17, `0,03 s` = 0,02%** — o overhead das Fases 17/18 é irrelevante. **Pico de RSS: 610 MB**, estabilizando a partir da 2ª página, sem vazamento. 5 páginas → 5 chamadas de OCR.
  - **Divergência contra a Fase 13 investigada**: aquela fase registrou pico de `2633 MB`, aqui são `610 MB`. Não é contradição — o número antigo é anterior à correção de retenção do `pixmap` (Fase 14) e a um arranjo em que a engine não era reaproveitada entre páginas. É o valor atual (610 MB) que vale para decidir sobre paralelismo, e foi o que se usou.
  - **Gargalo**: o OCR, 97,9%. Como modelo, prompt, estratégia e resolução estão fora de escopo por regra da fase, **o teto de qualquer otimização permitida é 2,1%** — e mexer no denoise (97% do pré-processamento) mudaria a imagem que entra no OCR, ou seja, mudaria o resultado.
  - **H5 paralelismo — DESCARTADO por medição.** Pré-requisito medido primeiro: **um único OCR já consome 6,0 núcleos**, exatamente o número de núcleos FÍSICOS da máquina (6 físicos/12 lógicos) — a folga aparente é só hyperthreading. Medição direta com 3 repetições alternando a ordem: sequencial `70,2 s` × concorrente `72,1 s` → **−2,7% (o concorrente é mais lento)**, com `+111 MB` de pico e `+259 MB` por engine adicional. A variação dentro de cada condição (9,1% e 5,1%) é **maior que o efeito**. Uma primeira execução isolada chegou a marcar +3,4%; repetida, virou −2,7% — exatamente o caso que a fase manda não concluir de uma medição só. Somado ao risco de reescrever o modelo de concorrência da Fase 10 (worker único + `queue.Queue` + `after()`), descartado.
  - **H2 cache — sem objeto**: 5 páginas, 5 chamadas de OCR, um `preprocess_image` e uma miniatura por página. **Não existe entrada repetida para cachear.** **H3 renderização — sem ganho**: leitura 0,1%, miniatura 0,03% e feita a partir da imagem já em memória. **H1 `.copy()` redundante no `preprocess_image` — NÃO adotado**: custa `4,1 ms/página` (0,011% do total), uma ordem de grandeza abaixo da variação de 1,1%, e é o que torna literal a garantia "a imagem original NUNCA é modificada"; removê-lo trocaria uma garantia explícita por uma dependência sutil em troca de nada medível.
  - **H4 retenção morta — ADOTADO (única alteração)**: `ui/app.py` atribuía `self._imagem_original` (26,8 MB) e `self._imagem_processada` (2,9 MB) a cada página, **escritas e nunca lidas** — sobraram das duas pré-visualizações que a Fase 10 removeu do topo da tela; o que a revisão usa é a miniatura JPEG. Medido em isolamento (5 repetições, sem OCR): **pico inalterado** (a retenção não está no instante do pico) e **29,8 MB → 0 MB retidos ao fim**. Nenhum ganho de tempo é reivindicado.
  - **Limitação do método, registrada para o futuro**: a variação DENTRO de uma sessão é 1,1%, mas o mesmo código oscila **~7% ENTRE sessões** (temperatura, carga de fundo, OneDrive). A execução "depois" marcou +7,0% no OCR, o que **não vem da alteração** — prova direta: `bench.py` nunca importa `ui/app.py`, o único arquivo alterado. Consequência: **este benchmark não distingue ganhos menores que ~7% entre sessões diferentes**; qualquer otimização futura que reivindique menos que isso precisa ser medida dentro de uma única sessão, intercalando as condições (foi o que se fez em H5).
  - **Conclusão**: o gargalo permanece onde estava e é intocável dentro das regras desta fase. Se um dia a operação precisar de mais velocidade, a evidência aponta que ela não virá de arrumar o código em volta do OCR, e sim de trocar o que executa o OCR (GPU, ou um modelo mais rápido com a precisão revalidada pelo procedimento da Fase 13) — decisão de projeto, não otimização.

**Fase 20 — Aprendizado com correções humanas (H1 e H2 CASO C; H3 e H4 CASO B; H5 CASO A — só a infraestrutura de coleta foi adotada)**: investigou se as correções que o operador faz na aba Revisão podem virar aprendizado seguro. **Nenhum aprendizado automático foi implementado**, e isso é o resultado da medição, não precaução. Quem chega fora de ordem fica no buffer até a sua vez. Isso não é zelo: o **`ContextoLote` é DEPENDENTE DE PREFIXO** (`ano_do_lote()` decide contra o que foi registrado até ali, com `MINIMO_DATAS_CONFIAVEIS`/`MAXIMO_DATAS_DIVERGENTES`/`FATOR_PREDOMINANCIA`), e os índices de `registros` são posicionais — consumidos por `POST /registros/{indice}/confirmar` e por `sinais_de_contexto`, que inclusive olha os VIZINHOS. O backend é single-process POR CONSTRUÇÃO (`_lotes`/`_ocr_engine`/`_data_manager` são globais de módulo; `uvicorn.run` sem `workers=`), e nesse regime a exclusão mútua que importa é um `threading.Lock` que já existe; a atomicidade ENTRE PROCESSOS do SQLite não compra nada utilizável e traria `check_same_thread` (as rotas síncronas rodam no threadpool), WAL, `busy_timeout` e `BEGIN IMMEDIATE` como superfície nova. Necessário porque um lease expira por LENTIDÃO, não por morte: o Worker antigo continua vivo e postando páginas de um Job que já é de outra tentativa, e deduplicar por número de página não resolve (ele pode entregar uma página que a tentativa nova ainda não alcançou).   - **Um segundo achado, mesma família de corrida**: entregar o resultado da ÚLTIMA página pode fazer a VPS concluir o Job (limpando `worker_id`/`fase_worker`) ANTES da chamada HTTP seguinte do mesmo Worker (a miniatura daquela página, um progresso, ou `/concluir`) executar. Resolvido separando os endpoints em dois grupos: **estritos** (download de arquivo, `/erro`, e a checagem de TENTATIVA — não de `fase_worker`/`worker_id` — embutida em `depositar_resultado_pagina` para `/paginas/{numero}`, o que permite reenviar a MESMA última página após a conclusão e continuar recebendo `"duplicado"`, nunca 409) e **lenientes** (`/paginas/.../miniatura`, `/progresso`, `/concluir` — sem posse válida, simplesmente não alteram nada e devolvem sucesso mesmo assim, porque são informativos/de liberação, nunca dado que precise de proteção).
  - **Terceiro achado, menor**: `cancelar()` não zerava `fase_worker`/`worker_id`/`lease_ate` — um lote cancelado continuava contando como `"aguardando_worker"` em `GET /api/worker/status`. Corrigido com a mesma limpeza que a conclusão normal já faz.
  - **Dois relógios de liveness, separados de propósito** (`LoteState.ultimo_progresso`, novo): o heartbeat prova que o PROCESSO do Worker está vivo; `ultimo_progresso` (atualizado a cada página aceita, cada progresso reportado, cada claim) prova que ele está PRODUZINDO — um processo pode bater heartbeat normalmente com o OCR travado. `varrer_leases_expirados` (função PURA, testável sem esperar o relógio de verdade) roda numa thread de fundo idempotente (`iniciar_vigilante_de_leases`, intervalo de 15 s — bem menor que `LEASE_S=120`/`LIMITE_SEM_PROGRESSO_S=600`).
  - `POST /lotes/{id}/cancelar` (novo, idempotente): único jeito de sair de `pendente`/`processando` sem concluir de verdade.
  - Verificação: suíte `teste/` **23/23**, backend **5/5** arquivos (incl. `teste_worker_api.py`, 11 blocos: autenticação, isolamento de `/leitor`, upload sem Worker nunca 500, claim atômico, download exige posse, caminho feliz completo até `concluido`, reenvio idempotente, lease expirado com recuperação sem perda de página, falha de documento inteiro, cancelamento, `/status` nunca expõe o token), e a **regressão OCR real (modo local, o caminho que a 26a já validava): 40/19/21/0 idêntico**, correções reais 27325/26319 continuam resolvendo.

  **26c — Worker Windows real** (pacote novo `worker/`: `__init__.py`, `config.py`, `cliente.py`, `heartbeat.py`, `execucao.py`, `__main__.py`, `testes/_servidor_real.py`, `testes/teste_worker_cliente.py`, `testes/teste_worker_real.py`; novos na raiz: `requirements-api.txt`, `requirements-worker.txt`, `.env.example`, `iniciar_worker.bat`): o processo Worker de verdade, testado ponta a ponta com PDF real e OCR real através do protocolo `/api/worker/*` sobre um servidor HTTP de verdade (socket real, não o transporte in-memory dos testes da 26b).
  - **Desvio deliberado do plano aprovado: D10 (worker embutido no modo desktop/`.exe`) NÃO foi adotada.** O plano original prevía `web/desktop_app.py` subir uma thread de Worker falando HTTP consigo mesmo via loopback, para "um único caminho de código". Revisto durante a implementação: dado a ordem de prioridades da missão (`preservar funcionamento atual > simplicidade > robustez > menor mudança necessária > manutenibilidade > ...`), o modo `local` (`produtor_ocr.py`, Sub-fase 26a) **já é** a história completa de "um processo só, sem Worker remoto" — já testado, já reconfirmado contra a baseline em toda sub-fase. Fazer o desktop falar HTTP consigo mesmo só por unificação de código path seria uma mudança maior e mais arriscada que o ganho de manutenibilidade compra. `web/desktop_app.py` continua **inteiramente intocado** — verificado por inspeção e por `config.modo() == "local"` sem nenhuma variável nova. `worker/` é um pacote genuinamente independente, para o cenário real da missão (PC Windows atrás de NAT, falando com a VPS via Tailscale).
  - **`worker/cliente.py` usa só `urllib.request`** (biblioteca padrão) — sem `requests`: o volume medido na auditoria (~15-20 KB/s sustentado) não justifica a dependência nova. Mapeia erros HTTP reais para três exceções com semântica clara: `ErroAutenticacao` (401/503 — configuração, não vale insistir sozinho), `ErroConflito` (409 — perda de corrida/posse, esperado em operação normal), `ErroTemporario` (rede fora do ar/5xx — vale backoff).
  - **`worker/heartbeat.py` roda numa thread própria**, independente do laço de OCR (D6) — sem isso, uma única folha demorada (~40 s + carregamento do modelo do PaddleOCR) deixaria o heartbeat minutos sem bater, e o lease (120 s no servidor) venceria à toa com o Worker vivo e trabalhando.
  - **`worker/execucao.py` roda o MESMO `pipeline.processar_uma_pagina`** que a VPS rodava internamente antes da Fase 26 — nenhuma regra de negócio nova. `_ler_imagem`/`_comprimir_para_miniatura` são cópia deliberada de `web/backend/produtor_ocr.py` (mesmo motivo que aquele módulo já documenta: importar de `web.backend.*` arrastaria `estado`/`armazenamento`, que escrevem no disco DA VPS — o Worker não deve tocar em nenhum dos dois).
  - **Um bug real, achado testando o valor de retorno de `entregar_pagina`**: o resultado (`"aceito"|"duplicado"|"obsoleto"`) estava sendo descartado — um Worker que perdesse a posse no meio de um Job continuaria rodando OCR em páginas que ninguém mais aplicaria. Corrigido levantando `ErroConflito` no caso `"obsoleto"`, propagando pelo mesmo caminho de exceção que já abortava o Job corretamente.
  - **Um achado de documentação da 26b, corrigido**: o docstring de `/progresso` afirmava que era o Worker quem reportava `total_paginas` de um PDF — incorreto, a VPS já calcula isso sozinha (`estado._descobrir_total_paginas`, contra a cópia que ela recebeu no upload, antes de qualquer Worker existir). `worker/execucao.py` nunca chama `pdf_reader.contar_paginas` por conta própria.
  - **Dependências separadas, validadas contra os imports reais**: `requirements-api.txt` (VPS em modo servidor — `numpy`/`openpyxl`/`PyMuPDF`/`fastapi`/`uvicorn`/`python-multipart`, **sem** OpenCV/PaddleOCR) e `requirements-worker.txt` (Worker — `opencv-python`/`numpy`/`paddleocr`/`paddlepaddle`/`PyMuPDF`, **sem** FastAPI/uvicorn/openpyxl). `requirements.txt` (raiz) continua a instalação completa, inalterada, usada por desktop/`.exe`/desenvolvimento.
  - Verificação: suíte `teste/` **23/23**, backend sem regressão, `worker/testes/teste_worker_cliente.py` (novo, 4 blocos, socket real — autenticação, claim/conflito, caminho feliz completo, erro de documento) **4/4**, e a verificação **decisiva** `worker/testes/teste_worker_real.py` (novo, lento, ~3-4 min): `worker.execucao.rodar` — o MESMO laço que `python -m worker` usa — processando `entrada/pdf/teste.pdf` através de um `uvicorn.Server` real, com PaddleOCR real: **40 registros, 19 CONFIRMADO, 21 REVISAO, 0 ERRO — idêntico à baseline**, correções reais 27325/26319 continuam resolvendo.
